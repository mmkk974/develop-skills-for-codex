# フェーズゲート判定基準

`spec -> plan -> task -> imple` の各フェーズで、次の必須項目を満たしたときだけ `pass` と判定する。

## 1. spec ゲート

- [ ] 解決すべき課題が1文以上で明確に書かれている
- [ ] 目標と非目標が分離されている
- [ ] ユースケースまたは利用シナリオがある
- [ ] 受け入れ基準が検証可能な文で定義されている
- [ ] 制約（技術/期限/運用）を列挙している
- [ ] リスクと未確定事項が列挙されている
- [ ] 意思決定ポイントが3件以上あり、推奨案/代替案が提示されている
- [ ] 回答が必要な確認質問が明示されている
- [ ] `REQ-*` が採番されている
- 判定方法: 全チェックで `pass`。1つでも未達なら `fail`。

## 2. plan ゲート

- [ ] `spec` の `REQ-*` を入力にしている
- [ ] 実装方針と非採用案の理由がある
- [ ] 影響範囲（コード、データ、運用）を示している
- [ ] テスト戦略（単体/結合/E2Eなど）を示している
- [ ] 移行戦略またはロールバック方針がある
- [ ] 設計上の意思決定ポイントに推奨案/代替案がある
- [ ] 判断保留事項に対する確認質問がある
- [ ] `PLN-*` と対応する `REQ-*` の紐付けがある
- 判定方法: 全チェックで `pass`。1つでも未達なら `fail`。

## 3. task ゲート

- [ ] `plan` をもとにタスク分解されている
- [ ] 全タスクに `TSK-*` が採番されている
- [ ] 各タスクに入力・作業内容・完了条件がある
- [ ] タスク依存関係が明示されている
- [ ] テスト実施タスクが含まれている
- 判定方法: 全チェックで `pass`。1つでも未達なら `fail`。

## 4. imple ゲート

- [ ] `TSK-*` ごとに実装内容が記録されている
- [ ] 変更ファイルとタスクが対応付けられている
- [ ] テスト結果（成功/失敗/未実施理由）がある
- [ ] 残課題と既知の制約が記録されている
- [ ] `REQ-* -> PLN-* -> TSK-* -> 実装/テスト` が辿れる
- 判定方法: 全チェックで `pass`。1つでも未達なら `fail`。
