# PR コメント判定ルール

## 1. 区分定義

- `must-fix`:
  - バグ、仕様違反、セキュリティ、データ破壊、権限不備、明確な回帰
  - コンパイル/ビルド失敗、テスト失敗、実行時例外を引き起こす指摘
- `should-fix`:
  - 可読性、保守性、将来の不具合予防、軽微なUX改善
  - 実害は低いが、低コストで改善価値が高い指摘
- `won't-fix`:
  - 誤読、誤検知、方針として非採用、過剰最適化
  - 現行スコープ外で、別チケット化が妥当な指摘

## 2. 判定手順

1. コメントの主張を1文で要約する。
2. 再現性または根拠コードを確認する。
3. 影響範囲を評価する（機能、性能、セキュリティ、運用）。
4. 修正コストと期限影響を評価する。
5. 区分を決定し、根拠を1-2行で記録する。

## 3. 優先順位

1. `must-fix`（高リスク順）
2. `should-fix`（低工数順）
3. `won't-fix`（理由を明記して保留/却下）

## 4. 追加確認が必要なケース

- 仕様書とコメントが矛盾している
- 再現手順が不足している
- 期待動作がレビュア間で不一致

上記は「追加確認」に分類し、質問を先に返す。
